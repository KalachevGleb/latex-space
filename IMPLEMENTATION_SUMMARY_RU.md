# Резюме реализации: Защита проектов и права пользователей

## Обзор

Реализованы три основные функциональности для Overleaf Community Edition:

1. **Защищённые проекты** - проекты, которые нельзя удалить
2. **Защищённые файлы** - файлы в проектах, которые нельзя удалять, изменять или переименовывать
3. **Права пользователей** - управление возможностью создания/загрузки проектов (базовые/полные права)

## Реализованная функциональность

### 1. Защищённые проекты

**Что реализовано:**
- Флаг `isProtected` в модели проекта
- API для установки/получения статуса защиты проекта (только для админов)
- Проверка при удалении проекта - защищённые проекты нельзя удалить
- Возвращается ошибка 403 с сообщением "This project is protected and cannot be deleted"

**API эндпоинты:**
```
POST /api/project/:Project_id/protection     - установить защиту (только админ)
GET  /api/project/:Project_id/protection     - получить статус защиты
```

### 2. Защищённые файлы

**Что реализовано:**
- Массив `protectedFiles` в модели проекта для хранения путей к защищённым файлам
- API для установки/получения списка защищённых файлов (установка только для админов)
- Проверки на уровне MongoDB операций:
  - Нельзя удалить защищённый файл
  - Нельзя переименовать защищённый файл
  - Нельзя заменить содержимое защищённого файла
- Выбрасываются соответствующие ошибки при попытке операций над защищёнными файлами

**API эндпоинты:**
```
POST /api/project/:Project_id/protected-files              - установить список (только админ)
GET  /api/project/:Project_id/protected-files              - получить список
GET  /api/project/:Project_id/is-file-protected/:file_path - проверить файл
```

### 3. Права пользователей

**Что реализовано:**

#### Базовые vs Полные права
- Поле `permissions` в модели пользователя ('basic' или 'full')
- **Базовые права** - пользователь НЕ может:
  - Создавать новые проекты
  - Загружать проекты
  - Клонировать проекты
- **Полные права** - пользователь может делать всё

#### Установка прав при создании пользователя
- В обычном режиме: новые пользователи получают `permissions: 'full'`
- В режиме peer-review: новые пользователи получают `permissions: 'basic'`
- Это настраивается автоматически при создании пользователя в `UserCreator.js`

#### Проверка прав
- Проверки добавлены во всех точках создания/загрузки/клонирования проектов
- Возвращается ошибка 403 с понятным сообщением при попытке запрещённой операции

#### Управление через API
- API для изменения прав пользователя (только для админов)
- API для получения прав пользователя (только для админов)

**API эндпоинты:**
```
POST /api/user/:user_id/permissions - установить права (только админ)
GET  /api/user/:user_id/permissions - получить права (только админ)
```

#### Интеграция с админ-панелью
- Поле `permissions` теперь возвращается в списке пользователей `/admin/users/list`
- Frontend может отображать и редактировать права пользователя

## Отличия от режима Peer-Review

### Старое поведение (только Peer-Review Mode)
- Глобальный режим для всей системы
- ВСЕ пользователи не могут создавать/удалять проекты
- Включается через системные настройки
- Нет гибкости

### Новое поведение (User Permissions)
- Права устанавливаются **индивидуально для каждого пользователя**
- Peer-review режим теперь влияет только на права **новых** пользователей
- Можно изменить права любого пользователя через API в любой момент
- Гораздо более гибкая система

## Безопасность

1. Все эндпоинты управления защитой и правами требуют прав администратора
2. Проверки защищённых файлов выполняются на уровне MongoDB операций
3. Проверки прав пользователя выполняются перед операциями с проектами
4. Все пути к защищённым файлам должны быть нормализованы и валидированы

## Миграция существующих установок

- Все существующие пользователи получат `permissions: 'full'` по умолчанию
- Все существующие проекты будут иметь `isProtected: false` по умолчанию
- Миграция базы данных не требуется - новые поля имеют значения по умолчанию
- Система полностью обратно совместима

## Примеры использования

### Защитить проект

```bash
curl -X POST http://localhost/api/project/PROJECT_ID/protection \
  -H "Cookie: overleaf_session2=..." \
  -H "Content-Type: application/json" \
  -d '{"isProtected": true}'
```

### Установить защищённые файлы

```bash
curl -X POST http://localhost/api/project/PROJECT_ID/protected-files \
  -H "Cookie: overleaf_session2=..." \
  -H "Content-Type: application/json" \
  -d '{
    "protectedFiles": [
      "/main.tex",
      "/chapters/intro.tex",
      "/images/logo.png"
    ]
  }'
```

### Установить базовые права пользователю

```bash
curl -X POST http://localhost/api/user/USER_ID/permissions \
  -H "Cookie: overleaf_session2=..." \
  -H "Content-Type: application/json" \
  -d '{"permissions": "basic"}'
```

### Проверить статус защиты

```bash
# Проверить защиту проекта
curl http://localhost/api/project/PROJECT_ID/protection \
  -H "Cookie: overleaf_session2=..."

# Проверить защиту файла
curl "http://localhost/api/project/PROJECT_ID/is-file-protected/%2Fmain.tex" \
  -H "Cookie: overleaf_session2=..."
```

## Тестирование

Для тестирования реализованной функциональности:

1. **Запустите систему:**
   ```bash
   cd develop
   bin/dev web
   ```

2. **Создайте тестовых пользователей** через админ-панель `/admin/register`

3. **Тестируйте защиту проектов:**
   - Создайте проект
   - Установите флаг защиты через API
   - Попробуйте удалить проект (должна быть ошибка 403)

4. **Тестируйте защищённые файлы:**
   - Создайте проект с файлами
   - Установите список защищённых файлов через API
   - Попробуйте удалить/переименовать защищённый файл (должна быть ошибка)

5. **Тестируйте права пользователей:**
   - Создайте пользователя
   - Установите ему базовые права через API
   - Войдите под этим пользователем
   - Попробуйте создать/загрузить/клонировать проект (должна быть ошибка 403)
